1. Enterprise architecture

Think in layers. The goal is not “more automation”; it is a maintainable quality platform with controlled dependencies.

CI / Quality Gate
GitHub Actions / Jenkins → install → lint → test → parallel shards → reports → quality gate → deployment decision
↓
Playwright Test
Projects, workers, retries, timeouts, fixtures, hooks, annotations, tags, reporters
↓
Test Layer
Business scenarios, assertions, test steps, test data references — keep business intent visible
↓
Domain Layer
Page Objects / components / API clients / service objects — expose actions, not raw locators
↓
Platform Layer
Fixtures, auth state, environment config, test-data factory, logging, API utilities, DB helpers
↓
System Under Test
Web UI ↔ APIs ↔ services ↔ databases / data lake / external dependencies

2. What actually happens during a test?

Worker

A worker process executes tests. Parallel workers allow independent tests to run concurrently.

Browser

A browser process hosts Chromium, Firefox or WebKit. Avoid treating the browser as the isolation boundary.

Context

A BrowserContext is an isolated browser session with separate cookies, storage and permissions.

Architectural rule: Prefer Context isolation over creating a browser for every test. It is usually cheaper and gives strong test isolation.
worker
 └── browser
      ├── context → test A → page(s)
      ├── context → test B → page(s)
      └── context → test C → page(s)

Test isolation ≠ new browser process for every test.

Tests

Describe behavior and business intent. Avoid implementation details.

Pages / Components

Encapsulate UI actions and selectors. A page object should say checkout(), not expose every CSS selector.

Fixtures

Compose reusable setup, dependencies and test-scoped resources without creating inheritance-heavy base classes.

Fixture composition

import { test as base } from '@playwright/test';

export const test = base.extend({
  apiClient: async ({ request }, use) => {
    const client = new UsersClient(request);
    await use(client);
  },

  loggedInPage: async ({ browser }, use) => {
    const context = await browser.newContext({
      storageState: 'auth/storage/user.json'
    });
    const page = await context.newPage();
    await use(page);
    await context.close();
  }
});

export { expect } from '@playwright/test';

4. Page Object Model: the architect's version

Good

await checkoutPage
  .addProduct('Laptop')
  .proceedToPayment()
  .placeOrder();

The test reads like a business workflow. Locators remain inside the page/component layer.

Avoid

await page.locator(
  '#root div:nth-child(4) button'
).click();

Raw selectors in tests couple business scenarios to UI implementation.

Trade-off: POM adds abstraction. That is valuable when workflows and selectors are reused, but excessive POM can hide test intent. Use page/component objects around meaningful behavior, not every DOM node.

5. Authentication and state

Best for scale

Authenticate once through an API or setup project and reuse storageState.

Isolation

Use separate contexts and, where necessary, separate user identities for tests that mutate state.

Security

Never commit credentials or generated auth state containing sensitive secrets. Inject secrets through CI.

// global/setup style concept
await request.post('/login', {
  data: { username: process.env.USER, password: process.env.PASSWORD }
});

// Save authenticated state
await context.storageState({ path: 'auth/storage/user.json' });

// Test config can consume that state
use: {
  storageState: 'auth/storage/user.json'
}
Key principle: Do not make every UI test pay the cost of a UI login unless login itself is the behavior being tested.

6. UI + API + database: hybrid testing

UI
Validate critical user journeys, rendering, navigation and integration behavior.
↕
API
Create data, perform fast setup, validate contracts, negative cases and service behavior.
↕
Data
Validate persistence, ETL transformations and business rules with controlled DB/query helpers.
Architectural trade-off: UI tests give high confidence in real user flows but are slower and more fragile. API/data tests are faster and easier to diagnose. Put most coverage at the lower layers and reserve UI automation for high-value journeys.

7. Scaling: workers, parallelism and sharding

If a 5,000-test suite takes 4 hours, simply increasing workers is not enough. First measure test duration, dependencies, fixture cost, serial constraints and flake rate.

TechniquePurposeTrade-off
WorkersRun independent tests concurrently on a machineMore CPU/RAM; too many workers can overload the SUT
ShardingSplit suite across CI machinesInfrastructure cost and balancing complexity
ProjectsRun browser/device/config variantsMultiplies execution volume
RetriesProtect pipeline from transient failuresCan hide real flakiness; never use as the primary fix
Smoke tagsFast release confidenceSmaller signal can miss broader regression defects
// Example CI strategy
Shard 1 ─┐
Shard 2 ─┤
Shard 3 ─┼──► Playwright tests ─► merge reports ─► quality gate
Shard 4 ─┤
Shard 5 ─┘

Target = balance test duration, worker capacity and application capacity.

8. Flakiness: diagnose before retrying

Async application

Prefer locator assertions and condition-based waits over arbitrary sleeps.

Test data collision

Generate unique data or isolate accounts/resources per worker.

Environment instability

Separate product failures from infrastructure failures using logs, traces and API health evidence.

// Prefer
await expect(page.getByRole('button', { name: 'Submit' }))
  .toBeEnabled();

// Avoid
await page.waitForTimeout(5000);
Reliability rule: Retry is a containment mechanism, not a defect fix. Track retry rate and quarantined tests as engineering metrics.

9. Observability and debugging

Trace

Use traces for action history, screenshots, DOM snapshots and timing context.

Video / screenshot

Capture on failure or for selected CI runs where storage cost is justified.

HTML / CI reports

Make failures searchable by suite, tag, browser, commit, owner and failure category.

Architect metric set: pass rate, flaky rate, retry rate, median/P95 test duration, suite duration, defect escape rate and infrastructure failure rate.

11. Architect trade-offs you should be ready to explain

Fixtures vs base classes

Fixtures favor composition and scoped setup. Base classes can be simpler initially but tend to create inheritance coupling.

API login vs UI login

API setup is much faster and reduces UI dependency. Keep dedicated UI-login tests for the login feature itself.

More workers vs more machines

Workers are cheaper to scale on one machine until CPU/memory or SUT capacity becomes the bottleneck. Sharding adds horizontal capacity.

Retries vs fixing flake

Retries improve pipeline resilience temporarily. Permanent flake reduction requires root-cause analysis.

POM vs direct locators

POM improves reuse and maintenance, but over-abstraction makes tests harder to understand.

UI coverage vs API coverage

UI gives end-to-end confidence; API/data checks provide faster, more diagnosable coverage. Optimize the portfolio, not one layer.

12. Migration strategy: Selenium/Cypress → Playwright

  1. Baseline: measure suite time, flake rate, coverage and business-critical journeys.
  2. Define target architecture: fixtures, POM/component model, API clients, auth strategy and reporting.
  3. Pilot: migrate a representative smoke/regression slice, not only easy tests.
  4. Dual run: keep the existing suite as the safety net while Playwright proves stability.
  5. Prioritize: migrate high-value, high-maintenance and frequently executed scenarios first.
  6. Scale CI: introduce workers, sharding and artifact/report strategy.
  7. Retire: remove duplicate legacy tests only after equivalent coverage and stable production evidence.
Architect answer: “I would not migrate 5,000 tests blindly. I would migrate by business risk and execution value while running both suites during the transition to avoid disrupting releases.”

import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  forbidOnly: !!process.env.CI,

  use: {

    video: 'retain-on-failure',

  ]

14. Interview-ready mental model

1. Isolate → BrowserContext

2. Compose → Fixtures

3. Encapsulate → Page/component objects

4. Accelerate → API setup + parallel workers + sharding

5. Stabilize → condition-based assertions + root-cause flake reduction

6. Observe → trace + reports + CI artifacts

7. Govern → quality gates + measurable engineering metrics

One-line architect summary: “I design Playwright as a layered, CI-first quality platform where tests express business behavior, fixtures manage dependencies, contexts provide isolation, APIs accelerate setup, and workers/shards provide scalable execution—with observability and quality gates built in.”
